# 信号监控状态机

> 本文档定义了信号监控服务的完整状态机，包括状态定义、转换条件、多标的处理和异常恢复。

---

## 状态定义

### 1. `idle` — 空闲

| 属性 | 值 |
|------|---|
| 描述 | 信号引擎已创建但未启动，或已手动停止 |
| 进入条件 | 初始化完成 / 用户手动停止 |
| 离开条件 | 用户启动监控 |
| 引擎行为 | 不获取数据，不计算指标，不检查规则 |

### 2. `watching` — 监控中

| 属性 | 值 |
|------|---|
| 描述 | 引擎正在监控市场数据，等待入场信号 |
| 进入条件 | 从 idle 启动 / 从 cooldown 冷却期结束 |
| 离开条件 | 入场规则被满足 → `entry_triggered` |
| 引擎行为 | 每个 bar：获取数据 → 计算指标 → 检查入场规则 → 记录日志 |

#### watching 状态下的操作

1. 接收新 bar 数据
2. 更新指标缓存
3. 计算所有 `features` 指标
4. 逐条检查 `entry_rules`（按 priority 排序）
5. 如果无规则满足 → 记录"未触发"日志，继续 watching
6. 如果有规则满足 → 进入去重检查

### 3. `entry_triggered` — 入场信号触发

| 属性 | 值 |
|------|---|
| 描述 | 入场条件满足，信号已生成并等待处理 |
| 进入条件 | watching 状态下入场规则满足且通过去重检查 |
| 离开条件 | 信号被确认/执行 → `position_open` / 信号超时 → `watching` |
| 引擎行为 | 生成 SignalEvent，发送告警，等待执行反馈 |

#### 信号超时处理

- 信号有 TTL（有效期），默认为 1 个 bar 周期
- 如果在 TTL 内未收到执行反馈，信号自动失效
- 失效后回到 `watching` 状态，记录"信号超时失效"日志

### 4. `position_open` — 持仓中

| 属性 | 值 |
|------|---|
| 描述 | 策略有活跃仓位，引擎监控出场条件 |
| 进入条件 | 入场信号被执行确认 |
| 离开条件 | 出场规则被满足 → `exit_triggered` |
| 引擎行为 | 每个 bar：获取数据 → 计算指标 → 检查出场规则 → 监控止损/止盈 |

#### position_open 状态下的操作

1. 接收新 bar 数据
2. 更新指标和持仓状态
3. 检查硬性出场条件（止损/止盈/追踪止损）
4. 检查信号出场规则（`exit_rules`）
5. 如果无出场条件满足 → 记录持仓状态日志，继续 position_open
6. 如果出场条件满足 → 进入 `exit_triggered`

### 5. `exit_triggered` — 出场信号触发

| 属性 | 值 |
|------|---|
| 描述 | 出场条件满足，出场信号已生成 |
| 进入条件 | position_open 状态下出场规则满足 |
| 离开条件 | 出场信号被执行确认 → `cooldown` |
| 引擎行为 | 生成出场 SignalEvent，发送告警，等待执行反馈 |

### 6. `cooldown` — 冷却中

| 属性 | 值 |
|------|---|
| 描述 | 上一笔交易完成后的等待期，暂不产生新信号 |
| 进入条件 | 出场信号被执行确认 |
| 离开条件 | 冷却期结束 → `watching` |
| 引擎行为 | 继续获取数据和计算指标（维持缓存），但不检查入场规则 |

#### 冷却期逻辑

```python
# 冷却期默认为 2 倍 bar 周期
cooldown_duration = 2 * bar_duration_seconds

# 每个 bar 检查冷却是否结束
if current_time - cooldown_start_time >= cooldown_duration:
    transition_to("watching")
```

## 状态转换表

| 当前状态 | 事件 | 目标状态 | 条件 |
|---------|------|---------|------|
| `idle` | 用户启动 | `watching` | 配置校验通过，数据源可用 |
| `watching` | 入场规则满足 | `entry_triggered` | 通过去重检查，不在冷却期 |
| `watching` | 无规则满足 | `watching` | 记录"未触发"日志 |
| `entry_triggered` | 执行确认 | `position_open` | 收到 execution-guard 的执行确认 |
| `entry_triggered` | 信号超时 | `watching` | 信号 TTL 过期 |
| `entry_triggered` | 执行拒绝 | `watching` | 收到 execution-guard 的拒绝反馈 |
| `position_open` | 出场规则满足 | `exit_triggered` | 止损/止盈/规则出场 |
| `position_open` | 无出场条件 | `position_open` | 继续监控 |
| `exit_triggered` | 执行确认 | `cooldown` | 平仓执行完成 |
| `cooldown` | 冷却结束 | `watching` | 冷却时间到达 |
| 任意状态 | 用户停止 | `idle` | 用户手动停止 |
| 任意状态 | 致命错误 | `idle` | 不可恢复的错误（数据源永久断开等） |

## 多标的状态管理

当策略监控多个交易对时，每个标的维护独立的状态机实例。

### 架构

```
┌──────────────────────────────────┐
│         SignalRuntime            │
│                                  │
│  ┌───────────────────────────┐  │
│  │  BTCUSDT 状态机            │  │
│  │  状态: watching            │  │
│  │  最后信号: 2026-03-12 10:00│  │
│  └───────────────────────────┘  │
│                                  │
│  ┌───────────────────────────┐  │
│  │  ETHUSDT 状态机            │  │
│  │  状态: position_open       │  │
│  │  入场时间: 2026-03-11 14:00│  │
│  └───────────────────────────┘  │
│                                  │
│  ┌───────────────────────────┐  │
│  │  SOLUSDT 状态机            │  │
│  │  状态: cooldown            │  │
│  │  冷却结束: 2026-03-12 16:00│  │
│  └───────────────────────────┘  │
│                                  │
│  共享: 数据获取、指标计算引擎    │
└──────────────────────────────────┘
```

### 规则

1. 每个标的的状态转换互相独立
2. 标的 A 的入场不影响标的 B 的状态
3. 但需遵守 StrategySpec 中的 `max_concurrent_positions` 限制
4. 如果已达最大持仓数，新的入场信号标记为 `blocked_by_max_position`

## 漏 bar 处理

### 场景

- 网络中断导致数据延迟
- 引擎重启导致 bar 缺失
- 数据源临时不可用

### 处理策略

| 漏 bar 数量 | 处理方式 | 说明 |
|-------------|---------|------|
| 1-3 个 bar | 补算 | 获取缺失 bar 数据，按顺序补算指标和规则 |
| 4-10 个 bar | 补算 + 告警 | 补算并发送"数据中断"告警 |
| > 10 个 bar | 重置 + 告警 | 完整重新加载历史数据，重建指标缓存 |

### 补算规则

1. 获取缺失期间的所有 bar 数据
2. 按时间顺序逐 bar 计算指标
3. 逐 bar 检查规则（但不发送实时告警，仅记录日志）
4. 如果补算期间发现应触发的信号，标记为"延迟信号"
5. 延迟信号的处理取决于当前状态和信号有效期

## 异常状态处理

### 数据获取失败

```
watching ─── 数据获取失败 ──► watching（跳过本 bar，记录错误）
                                │
                          连续失败 3 次
                                │
                                ▼
                        发送数据中断告警
                                │
                          连续失败 10 次
                                │
                                ▼
                        transition_to("idle")
                        发送引擎停止告警
```

### 指标计算异常

- 如果某个指标计算失败（如除零错误），跳过本 bar 不生成信号
- 记录错误日志，包含具体的指标名称和错误信息
- 不影响下一个 bar 的正常计算

### 状态持久化失败

- 如果状态持久化失败，立即重试 3 次
- 3 次重试均失败 → 发送告警，但继续运行（使用内存状态）
- 持久化恢复后立即同步最新状态
